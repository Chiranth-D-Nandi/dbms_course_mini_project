# Database Technology Choice & Architecture Justification

This document provides the technical justification and architectural rationale for employing a **hybrid dual-database architecture** combining **MySQL 8.0 (Relational / SQL)** and **ChromaDB (Vector Similarity Database)** in the Tatkal High-Concurrency Train Booking System.

---

## 1. Architectural Overview & Workload Separation

Modern enterprise systems require distinct storage engines optimized for fundamentally different query patterns. A railway booking system encompasses two diametrically opposed computational workloads:

1. **Transactional OLTP Engine**: Strict ACID properties, sub-millisecond row locks, zero tolerance for phantom reads or double-allocations, foreign key integrity, and financial accounting.
2. **Cognitive Information Retrieval**: High-dimensional semantic search over unstructured train route descriptions, natural language station intents, and complex railway policy FAQs.

```
                           +----------------------------------------+
                           |              User Request              |
                           +----------------------------------------+
                                       /                \
                                      /                  \
                        Structured Operations      Semantic Inquiries
                       (Bookings, Seats, PNRs)   (Train & Policy Search)
                                    /                      \
                                   v                        v
                    +--------------------------+  +--------------------------+
                    |    MySQL 8.0 (InnoDB)    |  |     ChromaDB (Vector)    |
                    |--------------------------|  |--------------------------|
                    | - ACID Transactions      |  | - 384-dim Embeddings     |
                    | - FOR UPDATE SKIP LOCKED |  | - Cosine Distance HNSW   |
                    | - Stored Procedures      |  | - Natural Language Query |
                    | - Strict Constraints     |  | - Policy Chunk Retrieval |
                    +--------------------------+  +--------------------------+
```

## 2. Why MySQL 8.0 (InnoDB) for Structured Railway Operations?

### A. ACID Guarantees & Concurrency Integrity
In a Tatkal rush scenario, thousands of users compete for fewer than 100 available berths. If two concurrent transactions read the same available berth and both book it, a catastrophic double-allocation occurs.
- **Atomicity**: The booking procedure (`sp_book_tickets`) updates `run_seat`, generates a `booking` header, and inserts multiple `passenger` records within a single atomic transaction block. If any step fails, the entire transaction rolls back.
- **Consistency**: Database-level `CHECK` constraints (e.g. `age BETWEEN 1 AND 120`, `halt_duration >= 0`), `FOREIGN KEY` cascades, and `UNIQUE` indexes ensure invalid states are rejected at the storage layer regardless of API logic.
- **Isolation**: InnoDB’s `REPEATABLE READ` snapshot isolation combined with `SELECT ... FOR UPDATE SKIP LOCKED` guarantees that concurrent sessions never lock or overwrite the same seat.
- **Durability**: InnoDB’s Write-Ahead Logging (WAL / `ib_logfile`) and doublewrite buffer ensure committed ticket transactions survive power failures and crashes.

### B. In-Database Stored Procedures for Sub-Millisecond Latency
Moving business logic into MySQL stored procedures (`sp_book_tickets`, `sp_confirm_payment`, `sp_cancel_booking`) eliminates multiple network round-trips between the web backend and the database. Seat reservation, fare computation, and hold generation occur directly in MySQL buffer memory in **< 5 milliseconds**.

### C. Automated Time-Based Events
MySQL's background event scheduler (`ev_release_expired_holds`) periodically runs every 30 seconds to reclaim unconfirmed seats whose 8-minute hold timer has lapsed, operating autonomously without requiring external cron jobs or worker queues.

## 3. Why ChromaDB for Vector Similarity Search?

### A. Limitations of Traditional Relational & Full-Text Search
Traditional SQL `LIKE '%pattern%'` or even MySQL `FULLTEXT` indexing relies purely on exact lexical matching and keyword stems. Lexical search fails in everyday human inquiries:
- A user searching for *"fastest luxury overnight train to Delhi with sleeper cabins"* will find zero results in SQL if the train description uses words like *"premier Rajdhani Express with 1A and 2A AC berths"*.
- A user asking *"can I get my money back if my Tatkal ticket is confirmed but train is late?"* cannot be answered by an exact SQL query against static policy tables.

### B. High-Dimensional Dense Embeddings
ChromaDB represents unstructured descriptions and railway regulations as 384-dimensional dense vectors generated by the `sentence-transformers/all-MiniLM-L6-v2` neural network.
- **Semantic Understanding**: Cosine distance captures contextual meaning, synonyms, and intent rather than keywords.
- **HNSW Indexing**: Hierarchical Navigable Small World (HNSW) graphs enable sub-linear retrieval time across large corpora.
- **Offline Self-Containment**: ChromaDB runs as a local persistent client (`./chroma_data`) with cached model weights (`./models/all-MiniLM-L6-v2`), completely eliminating third-party API dependencies or external cloud network calls.

## 4. Comprehensive Comparison Matrix

| Evaluation Dimension | MySQL 8.0 (InnoDB) | ChromaDB (Vector DB) | Why Neither Alone is Sufficient |
| :--- | :--- | :--- | :--- |
| **Primary Data Model** | Relational tables (Rows & Columns) | Document embeddings & vector spaces | Relational cannot efficiently index dense 384-dim vectors; Vector DB cannot enforce relational integrity. |
| **Transaction Semantics** | Full ACID with 2-Phase Commit | Eventual consistency (Append / overwrite) | ChromaDB has no transactional locks; booking tickets in ChromaDB would cause rampant race conditions. |
| **Concurrency Control** | Row-level locking (`FOR UPDATE SKIP LOCKED`) | File-level persistence locks | ChromaDB has no row-level mutexes for competitive seat allocation. |
| **Query Mechanism** | SQL (Declarative, JOINs, Grouping, Windows) | Vector distance (Cosine, L2, Dot Product) | SQL cannot calculate semantic similarity; Chroma cannot perform multi-table relational JOINs. |
| **Integrity Enforcement** | CHECK, ENUM, FOREIGN KEY, UNIQUE | Schema-free metadata dictionaries | Chroma cannot validate foreign keys or assert passenger age bounds. |
| **Ideal Workload** | Seat inventory, Bookings, Payments, Users | Train catalog search, FAQs, Cancellation policies | **Combined, they deliver enterprise ACID reliability with modern semantic intelligence.** |
